# Frontend

**Location**: `frontend/`  
**Phase**: 2 (Cloud Architecture)  
**Hosting**: S3 + CloudFront

---

## Current State

The existing app is a single-file Streamlit application (`app.py`). Streamlit is not hostable as a static site — it requires a running Python server. The cloud target is a static HTML/JS site that does the same job without a server.

---

## Technology Decision

**Default choice**: Minimal vanilla HTML/JS (`index.html` + `app.js` + `styles.css`)  
**Escape hatch**: Vite + minimal JS build if chart complexity becomes a blocker

The current Streamlit app has interactive Plotly charts with:
- Dual Y-axes
- Multi-select column controls
- Dynamic column awareness (different columns present in MHD vs BM3 logs)

Reproducing this in vanilla JS is non-trivial. **If the chart work stalls, switch to Vite + a lightweight charting library (e.g., Chart.js or Plotly.js) rather than fighting vanilla JS for chart interactivity.** The build artifact is still a static site — fully hostable on S3/CloudFront. Don't lose weeks on charting when the chart isn't the differentiator.

## Application Flow

### 1. Upload screen

- File input: accepts `.csv` only
- Optional fields (inform engine config, stored in DynamoDB):
  - Platform selector: MHD / BM3 (affects column mapping in engine)
  - Tune stage selector: Stage 1 / Stage 2 / E30 / E50 (optional; affects thresholds)
- On submit:
  1. `POST /upload` → receives `job_id` + `upload_url`
  2. `PUT` file directly to `upload_url` (S3 presigned PUT)
  3. Transition to polling screen

### 2. Polling screen

- Show a loading indicator with a reassuring message ("Analyzing your log…")
- Poll `GET /result/{job_id}` every 2–3 seconds
- On `status: processing` → keep polling
- On `status: complete` → render results screen
- On `status: failed` → show error message from `error_message` field
- Add a timeout after ~60 seconds — if still `processing`, show "Analysis is taking longer than expected. Try refreshing."

```js
async function pollResult(jobId) {
  const maxAttempts = 20;
  for (let i = 0; i < maxAttempts; i++) {
    await sleep(3000);
    const res = await fetch(`${API_BASE}/result/${jobId}`);
    const data = await res.json();
    if (data.status === 'complete') return data.report;
    if (data.status === 'failed') throw new Error(data.error_message);
  }
  throw new Error('Analysis timed out.');
}
```

### 3. Results screen

See [product-ux.md](product-ux.md) for the full UX design of the results output. Summary:
- Overall score + severity lane (stop / mention / normal)
- Per-finding cards with severity, explanation, and action
- Chart: RPM, boost, AFR, timing over the log timeframe
- "What to send your tuner" copyable pre-written message
- Shareable URL (`/result/{job_id}` — this URL is valid for 24 hours)

---

## Shareable URL

The results page URL is `https://{domain}/result/{job_id}`. When a user lands on this URL directly (shared from a tuner, or bookmarked), the frontend should:
1. Extract `job_id` from the path
2. Skip directly to polling/results — no upload screen
3. If the job is expired (DynamoDB TTL deleted it), show a graceful "This result has expired" message

Implement this with a simple URL router in `app.js` — check `window.location.pathname` on load.

---

## Chart Implementation

The chart needs to show (at minimum):
- RPM (left Y-axis)
- Boost pressure (right Y-axis)
- AFR (right Y-axis)
- Timing advance (right Y-axis)

Time or log index on X-axis. WOT segments should be visually highlighted.

**Plotly.js** is the closest equivalent to the existing Streamlit Plotly chart and produces nearly identical output. It's large (~3MB), but fine for a tool where the user is already uploading a file. Include it from a CDN rather than bundling.

If using vanilla JS with Plotly.js CDN:
```html
<script src="https://cdn.plot.ly/plotly-latest.min.js"></script>
```

## Deployment

The CI/CD pipeline (see [cicd.md](cicd.md)) syncs `frontend/` to the S3 frontend bucket on merge to `main`. After sync, it invalidates the CloudFront distribution so users get the new version immediately:

```bash
aws s3 sync frontend/ s3://bee58-frontend-${ENV}/
aws cloudfront create-invalidation --distribution-id ${CF_DIST_ID} --paths "/*"
```

---

## Environment Configuration

The frontend needs to know the API Gateway base URL, which differs between dev and prod. Use a build-time injection approach — generate a `config.js` file during deployment:

```js
// frontend/config.js (generated by CI, not committed)
window.BEE58_CONFIG = {
  apiBase: 'https://api-id.execute-api.us-east-1.amazonaws.com'
};
```

`index.html` loads `config.js` before `app.js`. `app.js` reads `window.BEE58_CONFIG.apiBase`. Never hardcode the API URL in committed code.
